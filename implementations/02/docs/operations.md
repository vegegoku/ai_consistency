# Payment service operations

Run one or more stateless application replicas against the same PostgreSQL primary. Do not route transfer writes to a read replica. Acknowledged successes are returned only after commit; payment IDs and ledger state are in PostgreSQL and survive process replacement. Use synchronous replication and durable storage when required by the recovery objectives.

## Reconciliation

A principal with `payments:admin` may call `GET /api/v1/admin/reconciliation`. Run daily and after restores or incidents. The report uses a repeatable-read snapshot and identifies payments with missing, extra, misdirected, incorrectly signed or unbalanced ledger entries; it also compares every persisted balance with `opening_balance + sum(signed_amount)`. Establish opening balances once during an audited migration. The application never changes them. The baseline is protected by a database trigger. Report contents include account identifiers and balances, so restrict the admin scope to operations staff and protect exported reports.

If `healthy` is false, freeze affected accounts through an audited administrative database workflow, preserve evidence and compare primary/WAL/backup state. Do not edit completed payments or ledger entries to make a report green. Resolve with an independently approved correction migration/compensating payment and retain the audit trail. The service exposes no account management endpoints.

## Authentication and network deployment

Configure a trusted issuer, audience and a PEM/JWKS URL with `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_PUBLIC_KEY_LOCATION`. JWTs require RS256 signatures and `iss`, `sub`, `aud`, `exp`, `iat`; OAuth scope is a space-separated `scope` string. Rotate signing keys through a trusted HTTPS JWKS endpoint. Customer ID equals `sub`; `account_permissions` grants additional debit/read/receive access. `PUBLIC` receive policy explicitly allows every authenticated submitter to submit to that destination; `OWNER_ONLY` and `ALLOWLIST` require ownership or an explicit receive grant. Customer and account states must both be ACTIVE. Source per-payment and daily outgoing limits are checked while its row is locked. Daily windows use processing time in UTC.

Production disables HTTP and requires TLS. Supply `QUARKUS_HTTP_SSL_CERTIFICATE_FILES`, `QUARKUS_HTTP_SSL_CERTIFICATE_KEY_FILES`; listen on 8443. Keep the management paths `/q/health`, `/q/metrics`, `/q/openapi` on a protected operational network or deny them at ingress. If terminating TLS upstream, use only a trusted proxy allowlist and validated forwarded scheme; never trust arbitrary client forwarded headers. Set the backend TLS certificate whenever possible. `PAYMENTS_TRUST_CORRELATION_HEADER` defaults false; enable it only behind a trusted gateway that replaces the header. Correlation IDs are UUIDs and are returned in `X-Correlation-ID`.

Rate limiting is a bounded, per-principal per-replica minute window. For horizontally scaled deployments, enforce the global rate quota at the trusted API gateway as well. Set connection pools and gateway concurrency against the primary capacity. Never log Authorization headers or raw request payloads. Audit financial attempts in payments and payment_issues; completed/rejected records contain principal, request correlation and timestamps. Structured API logs include correlation, payment ID, HTTP status, error code and latency. OpenTelemetry handles HTTP traces; configure an OTLP collector. Micrometer exposes requests, completion/rejection code, replay, retry, lock timeout, latency and unexpected failure metrics.

## Database roles and migrations

Run Flyway with a dedicated schema owner during deployment, then set `QUARKUS_FLYWAY_MIGRATE_AT_START=false` for runtime replicas. Runtime credentials need CONNECT/USAGE, SELECT on customers/accounts/account_permissions/payments/ledger_entries/payment_issues, INSERT on payments/ledger_entries/payment_issues, UPDATE on accounts/payments, and USAGE/SELECT on identity sequences. Restrict account UPDATE to available_balance/version/updated_at. Revoke DELETE/TRUNCATE and all schema CREATE/ALTER privileges; triggers additionally reject mutation of ledger/audit and final payments. Migration owner credentials must never be available to runtime pods. Compose deliberately uses a development superuser and must not be used as a production role template. Supply all secrets from a secret manager, rotate credentials, require PostgreSQL TLS (`sslmode=verify-full`) and restrict network access.

## Backups and restoration

Set recovery objectives and enable encrypted base backups plus continuous WAL archiving. Take `pg_dump -Fc` with a dedicated backup role; encrypt and store off-host with tested retention. Restore to an isolated database with `pg_restore --no-owner`, then restore/roll forward WAL if applicable. Run Flyway validation, compare payment/ledger counts and execute reconciliation before traffic is enabled. Test a full restore at least quarterly and record recovery time and point. Back up the account opening baseline and permission/audit tables with ledger data. Do not back up or commit application secrets.

## Retention and incidents

`payments.retention-years` (default 7, env `PAYMENTS_RETENTION_YEARS`) documents the minimum business retention; adapt it to applicable legal requirements before deployment. No automatic financial deletion is implemented: immutable records are retained indefinitely unless an approved archive migration meets that policy, legal holds and reconciliation requirements. Configure log/audit export retention in the logging platform; store no tokens or uncontrolled payloads. Backups must follow the same minimum retention and legal hold policy.

For a 503 or response loss, query the original ID or retry the same canonical instruction with the same payment ID. Never invent a replacement ID to resolve an unknown commit. For 409 definitive rejections, fix the business condition and send a newly authorized instruction with a new ID. For lock timeouts, inspect long transactions and pool saturation; do not kill a session without evaluating unknown commit outcomes. Preserve correlation IDs in incident tickets. A database outage fails readiness; failed execution rolls back, and transient errors are never persisted as rejections. Monitor rejection spikes, readiness failures, invariant errors, lock waits and reconciliation alarms.
