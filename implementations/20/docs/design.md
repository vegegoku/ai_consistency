# Implementation design

The source requirements are authoritative. All technical choices are autonomous as directed by AGENTS.md. The chosen single Quarkus service uses Java 21, JDBC and PostgreSQL rather than an ORM, so the transaction boundary, conflict behavior and lock ordering remain explicit. A distributed/asynchronous transfer pipeline was excluded because balances must update synchronously and atomically. An in-memory idempotency cache was excluded because replicas/restarts must preserve exactly-once financial effects.

The API chooses one negotiated response format, authenticates the JWT principal and scopes, applies a shared database rate limit, and parses a bounded UTF-8 document. Strict Jackson streaming preserves decimal lexical precision and detects duplicate keys. XML StAX forbids DTDs/entities/resource resolution, attributes/namespaces and nesting beyond root/field. Both map to one immutable validated command; amount is exact scale three, timestamp is an instant, and purpose/notes are trimmed. Fingerprints serialize an unambiguous ordered array of normalized fields and hash SHA-256.

Each transfer uses one JDBC transaction. `INSERT ... ON CONFLICT DO NOTHING` reserves the unique payment UUID, blocking duplicate contenders until the winner resolves. Replays compare the stored fingerprint and requester before returning the stored result. New payments lock both account rows using database `ORDER BY id FOR UPDATE`. Ownership/delegated debit permissions, destination receive policy, states, currency, account limit and available funds are checked under lock. Business rejection is finalized without balance changes. Success updates debit and credit, appends both signed ledger rows and finalizes the payment. A deferred database constraint trigger verifies completed-payment count/sum at commit; immutable-record triggers protect final payments and ledger rows. Exceptions roll back everything. Two bounded retries handle serialization/deadlock SQL states with the same logical UUID.

The service returns only after commit. Metrics are emitted using a failure-isolated helper; logging and timing occur in a response filter without affecting committed state. Readiness uses pooled database health. Query/replay reads persistent state, allowing stateless application restart. Reconciliation compares account state with a stored opening baseline and validates balanced two-entry completed payments. The admin API exposes a report for external scheduling. Financial retention is an operational archive horizon, never an automatic deletion mechanism.

The test strategy uses strict-parser unit tests, HTTP integration tests and real PostgreSQL containers. Injectable transfer observation permits a test alternative to fail immediately after debit; no public failure-injection API exists. Concurrent duplicate, competing withdrawal and opposing-direction workloads exercise unique constraints and row locks. A packaged HTTPS smoke workload supplements CI with process-restart and measured 100-RPS evidence.
