# Operations

Deploy stateless replicas with PostgreSQL as the durable authority. Terminate TLS directly in Quarkus with `QUARKUS_HTTP_SSL_CERTIFICATE_FILES` and `QUARKUS_HTTP_SSL_CERTIFICATE_KEY_FILES`, set `QUARKUS_HTTP_INSECURE_REQUESTS=disabled`, and keep `PAYMENTS_REQUIRE_TLS=true`. Direct TLS is the default trust model. Do not enable arbitrary forwarding headers to bypass secure transport checks. Restrict `/q/*` on the network to operators; expose `/q/health/live`, `/q/health/ready`, and `/q/metrics` to the appropriate probes and collectors only. Enable the OTLP endpoint for distributed traces. JWT RS256 verification uses configured issuer, audience and JWKS/public key location. Tokens must contain `sub`, `exp` and space separated `scope`.

Each customer principal can debit their own accounts or accounts delegated in `account_permissions.can_debit`. An active JOD destination with `receive_allowed=true` is a permitted recipient for every authorized sender; recipients can opt out by changing that policy flag. No account details are returned on hidden-account failures. Payment status is visible to the initiating principal only. Operations users need `payments:admin` for reconciliation. Grant account policy changes only through controlled database administration; the service has no administrative mutation endpoint.

Use separate migration-owner and runtime roles in production. Run Flyway migrations in the deployment job using the owner credentials; disable app migration with `QUARKUS_FLYWAY_MIGRATE_AT_START=false`. Grant runtime `SELECT` on accounts/customers/account_permissions/payments/ledger_entries/reconciliation_issues, `INSERT` on payments/ledger_entries, update of only balance/version/updated_at on accounts and status/rejection_code/processed_at on payments, sequence USAGE for ledger IDs, and SELECT/INSERT/UPDATE on request_limits. Never grant ledger UPDATE/DELETE, table ownership, trigger manipulation or arbitrary DDL to the runtime role. Database triggers also reject ledger edits and changes to finalized payments. Store credentials, private TLS keys and identity configuration in a secrets manager; local passwords and test JWT keys have no production role.

## Reconciliation

Establish `accounts.opening_balance` when accounts are created. It is an immutable operational baseline and must only be changed as part of an audited data migration with balancing financial records. At least daily and after each incident, run `SELECT * FROM reconciliation_issues` in a repeatable-read snapshot, or call `GET /api/v1/admin/reconciliation` with an admin token. Any result is an incident. The report compares each balance with its opening baseline plus ledger sum and checks completed payments have exactly two balanced linked entries. Tests deliberately alter an account fixture and assert detection. Freeze affected accounts and investigate audit records. Never fix a financial discrepancy by editing immutable ledger records; issue an independently approved compensating transfer or controlled accounting migration.

## Backups and restore

Enable encrypted daily full backups plus continuous WAL archiving for point-in-time recovery; choose RPO/RTO with the business. Example local logical backup: `docker compose exec -T postgres pg_dump -U payments -Fc payments > payments.dump`. Store encrypted copies in an access controlled offsite bucket. Quarterly restore drills must restore to an isolated PostgreSQL instance (`pg_restore --no-owner --dbname=payments payments.dump`), apply any pending migrations, run reconciliation, verify known payment IDs and account balances, and record actual recovery time and integrity results. Never point tests at a live production database.

## Incidents and uncertainty

For 503, lock timeout, dropped connection or lost HTTP response, query the original payment ID, then retry the exact original instruction using that ID. A 409 payload conflict requires caller investigation; do not invent a new ID automatically. Durable REJECTED outcomes remain definitive. Stop unsafe upstream retries during a database outage. Readiness reflects database connectivity. Investigate lock/retry metrics, database wait events and connection pool saturation; ordered row locking reduces deadlocks and each attempt has a 2 second lock timeout and 5 second SQL timeout with at most three attempts. Unexpected transactional failure rolls back all mutations. Response failure after commit does not reverse a payment.

Monitor `payments_outcomes_total`, `payments_replays_total`, `payments_retries_total`, `payments_lock_timeouts_total`, `payments_errors_total`, `payments_requests_total` and latency histograms. Logs contain only correlation ID, valid payment ID, status, code and duration. Restrict audit access and configure your collector's retention without logging payloads, authorization headers or financial account data. `X-Correlation-ID` accepts only canonical UUID-like values and is used solely as a diagnostic identifier, never authorization.

## Retention

The deployment policy setting `PAYMENTS_RETENTION_DAYS` defaults to 2555 (seven years). This is a documented minimum for operators, not an automatic deletion timer. Retain payment, ledger, initiating principal and baseline records for at least that period and longer where legal holds or applicable law require it. Review retention with local counsel. The application never deletes financial records; controlled archival must preserve reconciliation and idempotency tombstones. Set operational JSON log retention in the log collector, normally 30 days with restricted audit archives for the legal period. Purge idle `request_limits` rows older than two days through a scheduled operator job. Conduct restore drills before any archive migration.
