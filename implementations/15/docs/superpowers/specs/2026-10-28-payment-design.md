# Payment service design
The copied requirements are the source of truth. Decisions are autonomous as explicitly instructed.
Use Java 21, Spring Boot MVC and plain JDBC with PostgreSQL/Flyway. Quarkus is recommended rather than required; Spring's explicit TransactionTemplate and JDBC support minimize persistence ambiguity. An ORM was considered but adds no benefit to the narrowly locked transfer operation. An asynchronous architecture would obscure synchronous commit outcomes and is excluded.
Strict JSON token and XML StAX parsers produce one immutable command. Canonical normalized fields are length-delimited and SHA-256 hashed. Registration uses PostgreSQL ON CONFLICT and a unique UUID key. Both account rows are locked in ID order. Durable business rejections and two-entry completed payments commit atomically; database triggers enforce immutability and ledger invariants. Bounded retries cover deadlocks, serialization and lock timeouts. Unknown infrastructure failures roll back and remain retryable.
JWT signature, issuer, expiry, audience and operation scopes are validated. Ownership comes from the subject mapped to customers, with explicit grants and destination restrictions. Queries conceal unrelated resources. Production defaults require HTTPS. Header correlation IDs are always generated (untrusted public headers are ignored). Observability never logs payloads or account identifiers.
Tests use real PostgreSQL through Testcontainers, including concurrency and a database trigger for rollback injection. Reconciliation compares signed ledger against opening balances. Operations, retention, migration, local Keycloak and performance scripts accompany the service.
