# Payment Backend Implementation Plan

**Goal:** Implement the supplied payment processing requirements as an isolated deployable service.
**Architecture:** One synchronous Java 21 Spring Boot service. Strict transport codecs feed immutable commands; JDBC transactions use a unique payment key, deterministic row locks, durable outcomes and append-only ledger entries. PostgreSQL is the only financial state store.
**Tech stack:** Maven, Spring Boot, JDBC, Flyway, PostgreSQL, OAuth JWT, JUnit, Testcontainers, Micrometer.
**Spec:** `payment-processing-requirements.md`.

The supplied AGENTS.md authorizes autonomous design and implementation. Native execution is used without further approvals.

## Tasks
- [x] Write parser/validation tests first, observe failure, implement strict JSON/XML shared command normalization and validation.
- [x] Write PostgreSQL acceptance tests first, implement migrations, idempotency, authorization, row-locked transfers, persisted rejections, reconciliation and rollback.
- [x] Implement authenticated endpoints, negotiated errors, request bounds, correlation IDs, rate limits, health, metrics and tracing.
- [x] Exercise JSON/XML parity, duplicate requests, competing debits, rollback, unknown accounts, authorization, media negotiation, XXE and durable retrieval.
- [x] Supply OpenAPI, Compose, production container, seed data, CI, local examples, load test and operations runbook.
- [x] Run `mvn verify` against PostgreSQL, review output, document limitations honestly.

## Review focus
- Duplicate keys, nested documents and scalar coercion must reject before financial work.
- A retry with expired instruction date still needs an unchanged canonical payload; fresh IDs are needed for corrected commands.
- Replay authorization must be checked before exposing stored outcomes.
- Failure after debit must abort payment, debit and ledger together.
- Corrupted balanced/missing ledger and opening baseline discrepancies must be reported.
