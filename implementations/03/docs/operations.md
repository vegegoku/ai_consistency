# Operations

Deploy stateless replicas behind authenticated TLS ingress or configure Quarkus server certificate/key and disable HTTP. The application rejects insecure financial requests by default. If TLS terminates at a trusted ingress, enable Quarkus forwarded headers only with a private network and explicit trusted proxy configuration. Do not expose health, metrics, or OpenAPI publicly. Configure JWT_PUBLIC_KEY to an HTTPS JWKS endpoint or mounted public key, JWT_ISSUER, JWT_AUDIENCE, DB_URL, DB_USER and DB_PASSWORD via a secret store. JWT scope `payments:write` is required for submission; `payments:read` for retrieval; `payments:admin` for reconciliation. Source customer ID must equal token `sub`, or an explicit debit grant must exist. Destination requires ownership or an explicit receive grant and receive_allowed=true.

Use a migration role for Flyway deployment and disable `quarkus.flyway.migrate-at-start` afterward for runtime. A runtime database role needs SELECT on customer/accounts/permissions/payments/ledger, INSERT on payments/ledger, UPDATE on accounts and pending payments, and USAGE on ledger identity sequence. Revoke DELETE, schema CREATE, all ledger UPDATE, and baseline UPDATE from runtime. PostgreSQL triggers reject financial mutation. Do not use superuser application credentials. Seed credentials are strictly for local development.

Run `GET /api/v1/admin/reconciliation` with an admin-scoped JWT after each deployment and daily using an external scheduler. It reports completed payments lacking exactly two balanced entries and balances inconsistent with opening_balance plus ledger sum. Preserve baseline amounts at account provisioning. An unhealthy report requires immediate investigation and pausing affected submissions via ingress. Never repair by deleting/editing ledger records; use reviewed compensating transfers and documented migration for baseline corrections. Database triggers enforce ledger count/balance at commit. Reconciliation must run in a repeatable-read snapshot (implemented in service) to avoid reporting concurrent changes as corruption.

Backups: enable encrypted physical backups and continuous WAL archival, with point-in-time recovery and monitored replication. Example local logical backup: `docker compose exec -T postgres pg_dump -U payments -Fc payments > payments.dump`. Restore to an isolated instance with `pg_restore --clean --if-exists`, using an administrative restore role; reconcile, verify a known payment and balances, and run replay verification before promotion. Test restores quarterly; record recovery-point and recovery-time objectives based on business policy.

Retention: `AUDIT_RETENTION_DAYS` is an operational retention policy variable (default 2555 days / 7 years); retain payments and immutable ledgers for at least that period subject to jurisdictional counsel. The service has no deletion endpoint. Archive in encrypted access-controlled storage and use separately reviewed migration/DBA jobs for legal retention changes. Configure platform log retention via `LOG_RETENTION_DAYS` (default 90); logs exclude tokens/payloads. Never place user text in logs.

Incident handling: correlate X-Correlation-ID and paymentId; check payment status before retry. A 503 or client timeout has uncertain outcome: query or replay the SAME payment ID, never generate a new one. A durable rejection requires a new ID for corrected instructions. Check readiness, connection saturation, lock timeout/retry metrics and PostgreSQL locks. Metrics include requests, completions, rejection codes, processing latency, replays, retries and lock timeouts. Enable OpenTelemetry with OTEL_DISABLED=false and configure OTLP export; unavailable telemetry must not decide financial correctness. JSON logs record correlation, payment ID, final status and latency without payloads. Retain security audit access controls and alert on elevated forbidden/idempotency conflicts.

Rate limiting is per principal per application replica, bounded by minute windows; enforce a global distributed quota at the ingress when scaling. Set REQUESTS_PER_MINUTE according to policy (default 600). For the 100 requests/second reference target use at least 6000 plus headroom and prepare sufficient balances. Run `k6 run -e TOKEN=... -e BASE_URL=https://... scripts/load.js`, preserve results with hardware and database settings. Performance is a target and is not claimed until measured in the deployment reference environment.
